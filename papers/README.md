# papers/ — result candidates

One directory per result candidate. A "result candidate" is a specific claim the
program might publish — a noise-threshold map, a sharp-constant conjecture, a
strong-local-passivity phase map, an optimized protocol, a failure boundary — together
with everything needed to check it.

## Layout

```
papers/
  <candidate-slug>/            # e.g. circuit-qed-noise-thresholds/
    notebook.py                # the analysis, re-runnable top to bottom against the
                               #   package (notebook.ipynb is equally acceptable)
    data/                      # every array behind every figure (npz/csv), with the
                               #   generating script or notebook cell identified
    draft/                     # the manuscript (tex/md) and figures
    MANIFEST.md                # the claim in one paragraph; which vacuum.* modules and
                               #   experiments/ files it uses; the build it was produced
                               #   from; audit status
```

Slugs are lowercase-hyphenated and name the claim, not the paper title.

The analysis file may be a `.py` script or a `.ipynb` notebook — what is required is
that it runs **top to bottom, headless, with no hidden state**, regenerating everything
under `data/` from the installed package. All thirteen candidates in this tree ship
`notebook.py`, because a script diffs, imports, and runs unattended; a notebook is fine
wherever the narrative is worth the JSON. Every `notebook.py` also takes `--quick`, a
smoke configuration of the same code path that writes its output outside `data/` (a
temporary directory, or `--out DIR`), so the archive is only ever regenerated by a full run.

## The admissibility rule

**Claims are admissible only from builds in which the full known-results suite passes.**

Concretely: before any number moves from `data/` into `draft/`, the entire regression
suite — every validation anchor of every implemented layer, plus the standing audits
(energy ledger, passivity, causality, precision) — must pass on the exact code state
that produced the number, and `MANIFEST.md` must record that run (date, pytest summary,
package version). The literature is the test suite; a claim from a build that cannot
reproduce the literature is not a claim, it is a bug report.

Corollaries:

- A candidate whose numbers came from an optimizer (`vacuum.opt`) must include the
  plain-numpy re-run of the optimized protocol; only round-trip-surviving numbers enter
  the draft.
- A candidate that touches an anomaly (an audit failure on validated code) does not go
  here until it has survived the full anomaly protocol in PLAN.md — precision
  escalation, lattice-artifact checks, the communication-vs-vacuum split, and two
  independent implementations. The priors are explicit: passivity, the quantum
  inequalities, and causality are expected to hold.
- Directories are cheap; open one as soon as a discovery target starts producing
  curves. Most candidates should die in `data/` without ever growing a `draft/` — that
  is the system working.
